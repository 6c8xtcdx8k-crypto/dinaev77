# Архитектура Styleberries

## Слои

```
src/
├── app/          # Маршруты (App Router): страницы витрины, кабинета, админки, API
├── components/   # UI-компоненты (server по умолчанию, client — только интерактив)
├── actions/      # Server Actions — единственная точка мутаций из UI
├── services/     # Доменная логика: каталог, заказы, промокоды, платежи, email
├── lib/          # Инфраструктура: Prisma-клиент, auth, корзина, деньги, константы
└── prisma/       # Схема БД и сид
```

Правило зависимостей: `app → components/actions → services → lib`. Страницы читают данные напрямую через сервисы (server components), мутации идут только через server actions, которые валидируют вход (Zod), проверяют права и делегируют сервисам.

## Модель данных

- **Product → Variant**: товар хранит цену/скидку/описание, вариант — конкретную комбинацию `размер × цвет` со своим SKU и остатком. Фильтры каталога и корзина работают на уровне вариантов.
- **Cart**: привязана к cookie-токену (`sb_cart`), поэтому работает для гостей; после входа закрепляется за пользователем.
- **Order + OrderItem**: позиции заказа — снимки (название, цена, размер, цвет на момент покупки). Изменение или удаление товара не искажает историю заказов.
- **OrderStatusHistory**: каждый переход статуса логируется с комментарием.
- **PromoCode**: `PERCENT` (значение в %) или `FIXED` (значение в копейках), с минимальной суммой, сроком и лимитом использований.

Деньги везде — **копейки (Int)**. Форматирование — только на выводе (`lib/money.ts`).

## Ключевые инварианты

1. **Списание остатков атомарно.** `createOrder` выполняется в транзакции; остаток списывается через `updateMany({ where: { stock: { gte: qty } } })` — при гонке заказ, которому не хватило остатка, откатывается целиком.
2. **Статусы заказа — state machine** (`lib/constants.ts → ORDER_STATUS_TRANSITIONS`). Недопустимые переходы отклоняются и в админке, и в сервисе. Отмена возвращает остатки на склад.
3. **Промокод учитывается в той же транзакции**, что и заказ, с проверкой лимита использований.
4. **Email не ломает заказ**: отправка — fire-and-forget вне транзакции.

## Платежи

`services/payments/index.ts` определяет интерфейс:

```ts
interface PaymentProvider {
  name: string;
  createPayment(input): Promise<{ paymentId; confirmationUrl }>;
}
```

Поток: оформление → `createPayment()` → redirect покупателя на `confirmationUrl` → провайдер подтверждает оплату → заказ переводится в `PAID`.

- **mock** (по умолчанию): внутренняя страница `/payment/mock/[orderId]` с кнопками «Оплатить»/«Отменить» — для разработки и демо.
- **Реальный провайдер (ЮKassa, Stripe…)**: реализуйте интерфейс (создание платежа через API провайдера, `confirmationUrl` — их страница оплаты), зарегистрируйте в `getPaymentProvider()`, и обработайте подтверждение в `src/app/api/payments/webhook/route.ts`: проверка подписи → поиск заказа по `paymentId` → `changeOrderStatus(orderId, "PAID")`. Переключение — переменной `PAYMENT_PROVIDER`.

## Доставка

Способы и тарифы описаны декларативно в `lib/constants.ts → DELIVERY_METHODS` (курьер 399 ₽, бесплатно от 5 000 ₽; пункт выдачи бесплатно). Для интеграции реальных служб (СДЭК, Boxberry…) замените расчёт `deliveryCostFor()` в `services/orders.ts` на вызов API службы и добавьте выбор ПВЗ на шаге оформления.

## Email

`services/email/index.ts` — два транспорта, переключаются `EMAIL_PROVIDER`:
- `console` (dev): письмо логируется и сохраняется HTML-файлом в `.emails/`;
- `smtp` (prod): Nodemailer с настройками `SMTP_*`.

Шаблоны — `services/email/templates.ts` (создание заказа, смена статуса).

## Аутентификация и права

- JWT (HS256, `jose`) в httpOnly cookie `sb_session`, TTL 30 дней; пароли — bcrypt.
- Роли: `CUSTOMER` / `ADMIN`. Админ-маршруты защищены в `app/admin/layout.tsx` (redirect) и продублированы в каждом admin-action через `requireAdmin()` — защита не зависит от UI.

## Масштабирование

**PostgreSQL.** Смените `provider = "postgresql"` в `prisma/schema.prisma` и `DATABASE_URL`, затем `prisma db push` (или заведите миграции: `prisma migrate dev`). Схема написана совместимо (без SQLite-специфики; автоинкремент номера заказа реализован в приложении и защищён unique-констрейнтом).

**Дальнейшие шаги по мере роста:**
- Поиск: сейчас `LIKE` по названию/описанию — при росте каталога заменить на Postgres full-text search или Meilisearch/Typesense (точка замены — `services/catalog.ts → buildWhere`).
- Ценовой фильтр каталога считается в памяти после выборки (чтобы фильтровать по цене со скидкой). При больших каталогах — материализовать `finalPrice` колонкой, обновляемой при изменении цены/скидки, и фильтровать в SQL.
- Изображения: сейчас URL-строки (сид генерирует SVG в `public/products/`). Для продакшена — загрузка в S3-совместимое хранилище, поле `url` менять не нужно.
- Кэширование витрины: страницы помечены `force-dynamic` для простоты; главную и карточки можно перевести на ISR (`revalidate`) с точечной инвалидацией из admin-actions.
- Очередь для email (BullMQ/pg-boss), когда объём писем станет заметным.

## Тестирование

`npm run smoke` (`scripts/smoke-test.ts`) прогоняет бизнес-логику против реальной БД: валидация промокодов, создание заказа со списанием остатков и очисткой корзины, недопустимые переходы статусов, отмена с возвратом остатков, отклонение заказа сверх остатка. Запускается с `NODE_OPTIONS=--conditions=react-server`, чтобы обойти guard `server-only` вне Next.js.
